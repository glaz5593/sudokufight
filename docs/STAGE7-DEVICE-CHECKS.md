# שלב 7: בדיקות במכשירים (למשה)

הבדיקות שמשלימות את תנאי ה"סיום" של שלב 7 (`docs/02-WORK-PLAN.md`), ושאי אפשר להריץ ב־Jest.
מה שאפשר לבדוק בלי טלפון כבר נבדק אוטומטית: `apps/server/test/remoteHost.contract.test.ts` מריץ את הקוד של האפליקציה מול השרת האמיתי.
הוא משחק משחק מלא, מנתק לשנייה, מנתק אחרי ה־grace, בודק מעבר לרקע, ומודד 200 דגימות RTT.

## הכנה (פעם אחת)

1. **שרת פיתוח במחשב:** מהשורש, `npm run server`.
   - חדר פרטי עם קוד עובד **רק בשרת שאינו production**.
   - שרת ה־Staging ב־Fly.io רץ עם `NODE_ENV=production`, ולכן הוא דוחה חדרים פרטיים וזהות פיתוח. ראו "p95 ב־Staging" למטה.
2. **כתובת השרת בטלפונים:** ב־`apps/mobile/.env.local` שמים `EXPO_PUBLIC_SERVER_HOST=<כתובת ה־IP של המחשב ברשת>`, למשל `192.168.1.20`.
   - **לא `adb reverse`:** חיבור דרך כבל USB לא מתנתק במצב טיסה, ואז בדיקות 2 ו־3 לא בודקות כלום.
   - שני הטלפונים והמחשב על אותה רשת Wi-Fi.
3. **האפליקציה:** ה־Development Build שכבר מותקן מספיק. שלב 7 לא הוסיף מודול native, ואין צורך בבנייה חדשה.
   מריצים `npm run mobile` ופותחים את האפליקציה בשני הטלפונים.
4. **שמות שונים:** השם בחדר הוא שם הפרופיל. בלי שם, מוצג `Dev_xxxxxx`. לכל טלפון יש מזהה פיתוח משלו, שנשמר בטלפון.
   - אם שלב 8 כבר מחובר והטלפון מחובר לחשבון, השרת מזהה אותו לפי החשבון. גם זה עובד מול שרת פיתוח.
5. **איך מגיעים למסכים:** במסך הבית, בשורה "פיתוח" בתחתית: "משחק מקוון" (`/dev/online`) ו"מדדי רשת" (`/dev/metrics`).
   - במסך "משחק מקוון" מופיעות כתובת השרת והזהות. כדאי לוודא שהכתובת היא של המחשב.
   - בזמן משחק, בפינה התחתונה יש כפתור קטן "ms". הוא פותח את מדדי הרשת מעל הלוח.

## בדיקה 1: שני טלפונים, משחק של 2 שחקנים

1. **טלפון א':** "משחק מקוון" ← סוג "מהיר" ← "צור חדר".
   - צריך לראות "בכניסה למשחק", ואחר כך "חדר פרטי" עם קוד בן 6 תווים.
2. **טלפון ב':** "משחק מקוון" ← מקלידים את הקוד בשדה "קוד החדר" (אותיות קטנות, רווח או מקף לא משנים) ← "הצטרף".
3. **המשחק מתחיל ברגע ששניהם בחדר.** בודקים:
   - [ ] אותו לוח בשני הטלפונים. אני תמיד בתכלת, והיריב בצבע השני.
   - [ ] לחיצה על משבצת ריקה מציגה מיד טבעת "ממתינה", ותוך רגע היא הופכת לנעילה עם טיימר של 8 שניות.
   - [ ] ספרה נכונה או שגויה מוצגת רק אחרי שהשרת עונה, ומופיעה גם בטלפון השני.
   - [ ] הטיימרים זהים בשני הטלפונים, גם אם השעונים של הטלפונים לא מכוונים.
   - [ ] הפרעות ותגובות עוברות לטלפון השני.
4. **כניעה:** בטלפון ב' לוחצים "כניעה" בכרטיס שלי.
   - [ ] נפתח "אתה בטוח שאתה רוצה להיכנע?", עם "ביטול" כפתור זהב בולט ו"כן, להיכנע" משני.
   - [ ] "ביטול" סוגר בלי כלום, והמשחק המשיך ברקע.
   - בפעם השנייה לוחצים "כן, להיכנע":
   - [ ] ב': "הפסד", ו"איך זה נגמר: נכנעת לפני שהלוח התמלא".
   - [ ] א': "ניצחון!", ו"היריב נכנע".
   - [ ] בשניהם: "משחק מדורג · מהיר", ו"חדר פרטי: הדירוג עוד לא מתעדכן".
5. **משחק עד הסוף:** חוזרים על 1–3, ומשחקים עד שהלוח מתמלא.
   - [ ] שני הטלפונים מגיעים למסך התוצאות עם אותו ניקוד ואותו מקום.

## בדיקה 2: מצב טיסה ל־5 שניות (Reconnecting… 15)

באמצע משחק (בדיקה 1, שלבים 1–3):

1. **טלפון ב':** מפעילים מצב טיסה, סופרים 5 שניות, ומכבים.
2. **מה רואים בטלפון א':**
   - [ ] תוך 3–5 שניות מהפעלת מצב הטיסה: "היריב מתנתק…", "המשחק מוקפא · כל הטיימרים עצורים", וטבעת **"Reconnecting... 15"** שיורדת.
   - [ ] הכרטיסים נשארים גלויים, והלוח והמקלדת לא מגיבים.
   - ההשהיה של 3–4.5 שניות היא הזמן שבו השרת מזהה טלפון ששותק: טלפון במצב טיסה לא סוגר את החיבור.
3. **מה רואים בטלפון ב':**
   - [ ] מיד: "החיבור שלך אבד · מתחבר מחדש… ניסיון 1", אחר כך "ניסיון 2", והלוח נעול עם "הלוח נעול עד שתחזור".
4. **אחרי כיבוי מצב הטיסה:**
   - [ ] ב': "חזרת למשחק · הכל סונכרן", והבאנר נעלם אחרי 2.5 שניות.
   - [ ] א': ההקפאה נעלמת והמשחק ממשיך.
   - [ ] בשניהם אותו לוח, אותו ניקוד, אותן נעילות, ואותו זמן בטיימר.
5. **‏2 שניות לכל היותר:** את הזמן סופרים **מהרגע שה־Wi-Fi חזר** (האייקון בשורת המצב), לא מכיבוי מצב הטיסה.
   החיבור מחדש ל־Wi-Fi לוקח לטלפון עצמו כמה שניות.
   - [ ] ב"מדדי רשת" של טלפון ב' ("ms" בפינה): "זמן חיבור מחדש" ו"זמן סנכרון".
     "זמן סנכרון" צריך להיות קטן מאוד. "זמן חיבור מחדש" כולל גם את הזמן שהרשת הייתה כבויה.

   - [ ] המסך נשאר עד שלוחצים "לתוצאות". אחרי הלחיצה: "ניצחון!" עם התגית "ניצחת בנטישה".
3. **טלפון ב':** מכבים את מצב הטיסה. יש שתי תוצאות תקינות, לפי מתי הרשת חזרה:

## בדיקה 5: ‏p95 של RTT, עד 150ms על 200 דגימות

- **בטלפון:** משחק מקוון פתוח (גם חדר שממתין לשחקן שני מספיק), ואז "ms" ← השורה "Ping (זמן הלוך ושוב)".
  - [ ] אחרי כ־3.5 דקות יש 200 דגימות. הספירה מוצגת ב"‎200 בחלון". ב־Development Build הטלפון שולח ping פעם בשנייה.
  - [ ] ה־p95 בירוק אם הוא עד 150ms, ובאדום אם הוא מעל.
  - [ ] אותו דבר ל"לקוח ← שרת", "שרת ← לקוח" ו"זמן עדכון פעולה", אחרי כמה מהלכים.
- **מהמחשב, עם ה־fake-client:**
  `npm run fake-client -- --code <קוד> --ping-every 500 --url ws://<שרת>:2567`. בסוף הוא מדפיס את RTT ב־p50 וב־p95.
- **‏p95 ב־Staging (‏4G, אותו אזור):** כרגע אי אפשר לבדוק את זה ב־Staging. הוא רץ במצב production, ושם אין חדרים פרטיים ואין זהות פיתוח.
  צריך החלטה של משה, אחת מאלה:
  1. **אפליקציית Fly נוספת לפיתוח:** למשל `sudoku-fight-dev` באזור `fra`, עם `NODE_ENV=development`.
     פורסים אותה לבדיקה, ומוחקים אחר כך: כל אחד יכול להיכנס אליה עם זהות פיתוח.
  2. **לחכות לשלב 9:** Matchmaking עם חשבונות, שעובד גם ב־production.
  3. **שרת במחשב דרך 4G:** מנהרה (למשל `cloudflared`), ואז המדידה כוללת גם את המנהרה.

## אם משהו נכשל

- את קוד השגיאה הקטן במסך "שגיאת חיבור" (למשל `notFound-522` או `network`) מעבירים ל־Claude.
- ב־Metro מודפסות שורות `[online] …` מכל טלפון: ניתוק, ניסיונות חזרה וסיבה. ה־reconnection token לא מודפס אף פעם.
- בשרת: `GET http://<שרת>:2567/dev/metrics` מחזיר את זמני הטיפול בפעולות.
