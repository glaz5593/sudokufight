# שלב 7: בדיקות במכשירים (למשה)

הבדיקות שמשלימות את תנאי ה"סיום" של שלב 7 (`docs/02-WORK-PLAN.md`), ושאי אפשר להריץ ב־Jest.
מה שאפשר לבדוק בלי טלפון כבר נבדק אוטומטית: `apps/server/test/remoteHost.contract.test.ts` מריץ את הקוד של האפליקציה מול השרת האמיתי.
הוא משחק משחק מלא, מנתק לשנייה בשלב השקט ובלעדיו, משחק בלי חיבור (ספרה שנספרת, וספרה במשבצת שנתפסה), מנתק אחרי ה־grace, בודק מעבר לרקע, ומודד 200 דגימות RTT.

> **בקצרה: `npm run dev:lan -- --write-env`** מהשורש, ואז `npm run mobile -- --clear` בחלון שני.
> הפקודה מוצאת את כתובת המחשב ב־Wi-Fi, כותבת אותה ל־`apps/mobile/.env.local`, טוענת את המאגר המדורג אם חסר, ומפעילה את השרת.
> אחר כך היא מדפיסה את הכתובת לבדיקה מהטלפון (`/health`), את אתר הניהול, פקודות ל־Windows Firewall ופקודות ל־`fake-client`.
> סעיפים 1 ו־2 כאן הם מה שהיא עושה, למי שרוצה ידנית. הפירוט ב־README, בסעיף "טלפונים ב־Wi-Fi".

## הכנה (פעם אחת)

1. **שרת פיתוח במחשב:** מהשורש, `npm run server` (או `npm run dev:lan`).
   - חדר פרטי עם קוד עובד **רק בשרת שאינו production**.
   - שרת ה־Staging ב־Fly.io רץ עם `NODE_ENV=production`, ולכן הוא דוחה חדרים פרטיים וזהות פיתוח. ראו "p95 ב־Staging" למטה.
2. **כתובת השרת בטלפונים:** ב־`apps/mobile/.env.local` שמים `EXPO_PUBLIC_SERVER_HOST=<כתובת ה־IP של המחשב ברשת>`, למשל `192.168.1.20`.
   - **לא `adb reverse`:** חיבור דרך כבל USB לא מתנתק במצב טיסה, ואז בדיקות 2 ו־3 לא בודקות כלום.
   - שני הטלפונים והמחשב על אותה רשת Wi-Fi.
3. **האפליקציה:** ה־Development Build שכבר מותקן מספיק. שלב 7 לא הוסיף מודול native, ואין צורך בבנייה חדשה.
   מריצים `npm run mobile` ופותחים את האפליקציה בשני הטלפונים.
4. **שמות שונים:** השם בחדר הוא שם הפרופיל. בלי שם, מוצג `Dev_xxxxxx`. לכל טלפון יש מזהה פיתוח משלו, שנשמר בטלפון.
   - אם שלב 8 כבר מחובר והטלפון מחובר לחשבון, השרת מזהה אותו לפי החשבון. גם זה עובד מול שרת פיתוח.
5. **איך מגיעים למסכים:** במסך הבית, בשורה "פיתוח" בתחתית: "משחק מקוון" (`/dev/online`) ו"מדדי רשת" (`/dev/metrics`).
   - במסך "משחק מקוון" מופיעות כתובת השרת והזהות. כדאי לוודא שהכתובת היא של המחשב.
   - בזמן משחק, בפינה התחתונה יש כפתור קטן "ms". הוא פותח את מדדי הרשת מעל הלוח.

## בדיקה 5: ‏p95 של RTT, עד 150ms על 200 דגימות

- **בטלפון:** משחק מקוון פתוח (גם חדר שממתין לשחקן שני מספיק), ואז "ms" ← השורה "Ping (זמן הלוך ושוב)".
  - [ ] אחרי כ־3.5 דקות יש 200 דגימות. הספירה מוצגת ב"‎200 בחלון". ב־Development Build הטלפון שולח ping פעם בשנייה.
  - [ ] ה־p95 בירוק אם הוא עד 150ms, ובאדום אם הוא מעל.
  - [ ] אותו דבר ל"לקוח ← שרת", "שרת ← לקוח" ו"זמן עדכון פעולה", אחרי כמה מהלכים.
- **מהמחשב, עם ה־fake-client:**
  `npm run fake-client -- --code <קוד> --ping-every 500 --url ws://<שרת>:2567`. בסוף הוא מדפיס את RTT ב־p50 וב־p95.
- **‏p95 ב־Staging (‏4G, אותו אזור):** כרגע אי אפשר לבדוק את זה ב־Staging. הוא רץ במצב production, ושם אין חדרים פרטיים ואין זהות פיתוח.
  צריך החלטה של משה, אחת מאלה:
  1. **אפליקציית Fly נוספת לפיתוח:** למשל `sudoku-fight-dev` באזור `fra`, עם `NODE_ENV=development`.
     פורסים אותה לבדיקה, ומוחקים אחר כך: כל אחד יכול להיכנס אליה עם זהות פיתוח.
  2. **לחכות לשלב 9:** Matchmaking עם חשבונות, שעובד גם ב־production.
  3. **שרת במחשב דרך 4G:** מנהרה (למשל `cloudflared`), ואז המדידה כוללת גם את המנהרה.

## בדיקה 6: הפרעות בשתי הקשות, החשכת הלוח והסוגים החדשים (D44–D47, 18.10.2026)

ההחלטות של משה מ־17.10.2026 (אפיון סעיף 7): אין גרירה. "הפרעה" בכרטיס של יריב ואז סוג בחלון. אין הפרעות מול בוט. כל הפרעה מחשיכה את הלוח. שלושה סוגים חדשים: מספרים מתערבלים, דיו ומקלדת מתערבלת.
ב־Jest כבר נבדקו החוקים, החלון, הרשת בלי גלילה, ההשהיה של 250ms, הסוגים לפי החדר, ו"אין הפרעות מול בוט". כאן בודקים מה שרואים ומרגישים רק בטלפון.

> **סדר העדכון: קודם השרת, ורק אחר כך האפליקציה.** כאן, מול `npm run server` במחשב, זה קורה מעצמו.
> ב־Staging: קודם deploy של השרת, ורק אחר כך מחלקים את ה־APK החדש. שרת ישן נותן לאפליקציה החדשה רק את שלושת הסוגים הישנים.

**הכנה:**
- השרת והטלפונים כמו בהכנה למעלה. אם Claude לא אמר אחרת, ה־Development Build שכבר מותקן מספיק: `npm run mobile -- --clear`.
- **רמה:** חשבון חדש הוא ברמה 1. אצלו שלושת הסוגים החדשים נעולים בחלון, וזו בדיקת הנעילה. את האפקטים עצמם בודקים כשהטלפון **מקבל** הפרעה מ־`fake-client`, שלא תלוי ברמה (סעיף 3 למטה).
- **גודל מסך:** חלק מהבדיקות בטלפון של 360×780dp (למשל S22), ופעם נוספת בטלפון נמוך יותר (כ־640dp), או עם "גודל תצוגה" גדול בהגדרות של Android.

### 3. שלושת הסוגים החדשים (טלפון אחד ו־`fake-client` שמפריע)

לכל סוג בנפרד, `fake-client` יוצר חדר שבו מותר רק הסוג הזה, ומפריע הרבה (רמה 5):

```
npm run fake-client -- --create --level 5 --speed 2 --rules '{"interferenceKinds":["scramble"]}'
```

הוא מדפיס קוד. בטלפון: "משחק מקוון" ← הקוד ← "הצטרף". כשיש לו נקודות, הוא מפריע לטלפון. אחר כך שוב עם `"ink"` ועם `"keypad"`. (ב־PowerShell: אם המירכאות נשברות, `--rules '{\"interferenceKinds\":[\"ink\"]}'`.)

- [ ] **מספרים מתערבלים:** הספרות בלוח מתגלגלות, בצבע של ה־fake-client, ולא יותר מפעמיים־שלוש בשנייה. חלק מהן אמיתיות. זה לא מרגיש מהבהב. הקשה על משבצת עדיין בוחרת אותה, והמקלדת לא משתנה. בסוף הכל חוזר.
- [ ] **דיו:** כתמים מכסים חלק מהלוח, ונמחקים בהדרגה לקראת הסוף. אפשר להקיש דרכם.
- [ ] **מקלדת מתערבלת:** המקשים מחליפים מקומות כל שנייה וחצי. **על כל מקש תמיד הספרה שהוא מזין**: מזינים כמה ספרות בזמן ההפרעה ובודקים. "ביטול בחירה" לא זז.
  - [ ] שמים אצבע על מקש ומחזיקים: הוא לא זז מתחת לאצבע.
  - [ ] הקשה בדיוק בזמן ההחלקה לא מזינה כלום (רטט קטן), ולא נספרת כטעות.
  - [ ] בסוף ההפרעה המקשים חוזרים ל־1–9 משמאל לימין.
- [ ] בכל אחד: 55fps בערך, בלי קפיצות (Perf Monitor, ‏`PERF.md`).
