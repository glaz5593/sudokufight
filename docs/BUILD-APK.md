# בניית APK במחשב: פקודה אחת, מתי שרוצים

קובץ APK לטלפוני הבדיקה נבנה **במחשב שלך**, בלי הענן של Expo, ובלי המגבלה של 15 בניות בחודש.
הענן (EAS) נשאר רק לגרסה שעולה לחנות.

## בקצרה

ב־PowerShell:

```powershell
cd C:\Users\mosheg\Documents\ReactNative\sudoku-fight
npm run apk
```

מחכים. בסוף מופיעה שורה שמתחילה ב־`APK:`, עם המיקום של הקובץ. הקובץ נשמר בתיקייה `apps\mobile\apk`.

כדי לבנות **וגם להתקין** על הטלפונים שמחוברים בכבל:

```powershell
npm run apk -- --install
```

## כמה זמן זה לוקח

| מתי | זמן |
|---|---|
| **בפעם הראשונה** | בערך 30 עד 45 דקות. המחשב מקמפל את כל הספריות. |
| **בפעמים הבאות** (שינוי בקוד, בטקסטים, בעיצוב) | בערך 2 עד 3 דקות. הקוד של המשחק (JS) נארז מחדש בכל בנייה, כדי שאף שינוי לא יתפספס. כל השאר כבר שמור מהפעם הקודמת. |
| **אחרי שינוי ב"שלד"** (חבילה חדשה, אייקון, הרשאה, Firebase) | בערך 5 דקות. הפקודה מזהה את זה לבד ובונה את תיקיית `android` מחדש. |
| **אחרי עדכון של Expo, או של ספרייה עם קוד native** | יותר: הספרייה מתקמפלת מחדש. לפעמים כמעט כמו בפעם הראשונה. |

בזמן הבנייה מודפסת כל דקה שורה קצרה: כמה זמן עבר, מה נבנה עכשיו, וכמה מקום פנוי בכונן C.

## מה הפקודה עושה

1. **בודקת את המחשב:** מקום פנוי בכונן C, ‏Java 17, ‏Android SDK, והקובץ של Firebase.
2. **מכינה את תיקיית `android`** מתוך הגדרות האפליקציה (`expo prebuild`), רק כשההגדרות השתנו מהפעם הקודמת.
3. **בונה גרסת release** עם Gradle. רק לטלפונים של 64 ביט (`arm64-v8a`): זה כל טלפון מהשנים האחרונות, וזה חוסך שלושה רבעים מהזמן ומהמקום.
4. **בודקת את הקובץ שיצא:** שהוא חתום, ושכתובת השרת באמת בתוכו.
5. **שומרת אותו** ב־`apps\mobile\apk`. נשמרים רק 3 הקבצים האחרונים, הישנים נמחקים לבד.

שם הקובץ אומר מה יש בו, למשל `sudoku-fight-1.0.1-a4b6c88-staging.apk`:

- `1.0.1`: גרסת האפליקציה (ראו "גרסה" למטה).
- `a4b6c88`: הקוד שנבנה (ה־commit ב־git).
- `-dirty`, אם מופיע: היו שינויים שעוד לא נשמרו ב־git.
- `staging`: השרת שהאפליקציה מתחברת אליו.

## גרסה

כל APK נושא מספר גרסה, למשל `1.0.1`, ורואים אותו באפליקציה: בתחתית **ההגדרות** ובתחתית **מסך הכניסה**.

- **שורה ראשונה:** "גרסה 1.0.1". זו הגרסה שמותקנת בטלפון בפועל (נקראת מהאפליקציה עצמה).
- **שורה שנייה, קטנה:** למשל `build a1b2c3d · staging`. הקוד שנבנה (ה־commit ב־git, עם `-dirty` אם היו שינויים שלא נשמרו), והשרת: `staging`, ‏`production`, ‏`local`, או הכתובת שניתנה ב־`--server`. בהגדרות מופיעה בסוף גם גרסת המנוע.

**הגרסה הראשונה היא `1.0.0`.** אחריה `1.0.1`, ‏`1.0.2` וכן הלאה. ה־APK הראשון עם הגרסאות נבנה כמו שהוא, כ־`1.0.0`.

**מכאן והלאה מעלים גרסה לפני כל APK חדש שמגיע לטלפונים** (Claude עושה את זה לפני כל APK שהוא מעביר למשה):

```powershell
npm run version:bump
```

הפקודה מעלה את המספר האחרון (`1.0.0` ל־`1.0.1`), ומדפיסה מה היה ומה נהיה. רק השדה `expo.version` ב־`apps\mobile\app.json` משתנה.

| פקודה | מה משתנה |
|---|---|
| `npm run version:bump` | ‏`1.0.0` ← ‏`1.0.1`. הרגיל, לכל APK. |
| `npm run version:bump -- minor` | ‏`1.0.7` ← ‏`1.1.0`. שינוי גדול יותר. |
| `npm run version:bump -- major` | ‏`1.4.2` ← ‏`2.0.0`. |
| `npm run version:bump -- --dry-run` | רק מדפיס, לא משנה כלום. |

**מספר הבנייה (versionCode)** נגזר מהגרסה, לבד (`app.config.ts`): ‏`1.0.0` הוא 10000, ‏`1.0.1` הוא 10001, ‏`1.2.3` הוא 10203. אנדרואיד מתקין APK מעל האפליקציה שבטלפון רק כשהמספר הזה לא קטן יותר, ולכן כל APK אחרי העלאת גרסה מתעדכן מעל הקודם, והנתונים נשארים. לכן גם האחרון והאמצעי מוגבלים ל־99.

- **בענן (EAS), לגרסה לחנות:** ‏EAS סופר את מספר הבנייה בעצמו (`appVersionSource: remote` ו־`autoIncrement` ב־`eas.json`), ומתעלם מהמספר של `app.config.ts`. את הגרסה שרואים (`1.0.1`) הוא לוקח מ־`app.json`, כמו כאן.
- שם הקובץ של ה־APK כבר כולל את הגרסה, למשל `sudoku-fight-1.0.1-a1b2c3d-staging.apk`.
- שינוי גרסה משנה את `app.json`, ולכן הבנייה הבאה מכינה את תיקיית `android` מחדש (בערך 5 דקות במקום 2 עד 3).

## לפני APK של גרסה חדשה: קודם השרת (מ־1.0.2)

**‏APK ‏1.0.2 (אימון בשלבים) נבנה רק אחרי שהשרת שלו כבר רץ:**

1. **השרת ל־Staging:** `fly deploy --ha=false` (‏README, "פריסה ל־Fly.io (Staging)"). ה־migration ‏0008 רץ לבד, ואין צורך ב־`db:seed-puzzles`. בודקים ש־`https://sudoku-fight-staging.fly.dev/health` מחזיר `"engine":"0.3.0"`.
2. **רק אחריו:** `npm run apk` (מול Staging), עם הגרסה 1.0.2 (`npm run version:bump`, בנייה 10002).
3. **‏APK מול Production** (`npm run apk -- --server production`) רק אחרי שגם שרת ה־Production עודכן (`docs/DEPLOY-PRODUCTION.md` סעיף 5).

- **למה:** APK ‏1.0.2 מול שרת ישן שומר את הכוכבים בטלפון, אבל הסנכרון וה־XP מחכים לשרת החדש, ואירועי השלבים נדחים ואובדים. הסדר המלא: [`RELEASE-CHECKLIST.md`](RELEASE-CHECKLIST.md), "גרסה 1.0.2".
- **וכך גם בעתיד:** בכל פעם שמספר השלבים גדל, נוסף סוג שלב, או נוסף שדה לאירועי השלבים, קודם השרת ורק אחר כך ה־APK.
- הבנייה, הפריסה וההעברה לטלפונים: כל אחת רק באישור של משה.

## לאיזה שרת האפליקציה מתחברת

| פקודה | שרת |
|---|---|
| `npm run apk` | **שרת הבדיקות** (staging), ‏`sudoku-fight-staging.fly.dev`. זה מה שצריך כמעט תמיד. |
| `npm run apk -- --server production` | שרת הייצור. |
| `npm run apk -- --server local` | השרת שרץ **במחשב שלך** (`npm run server`). הפקודה מוצאת לבד את הכתובת של המחשב ברשת ומדפיסה אותה. |

לגבי `--server local`:

- הטלפונים צריכים להיות **באותו Wi-Fi** כמו המחשב.
- החיבור בלי הצפנה, אז זה רק לבדיקות בבית.
- אם הטלפון לא מגיע לשרת, כנראה חומת האש של Windows חוסמת. `npm run dev:lan` מדפיס את הפקודה שפותחת אותה (ב־README, "טלפונים ב־Wi-Fi").
- הכתובת של המחשב נכנסת **לתוך** ה־APK. אם היא משתנה (למשל אחרי שהמחשב התחבר מחדש לרשת), בונים שוב עם `--server local`.
- אפשר גם לתת כתובת בעצמך, למשל `--server 192.168.1.50`. כתובת כזו, בלי פורט, היא כמו `local`: פורט 2567, בלי הצפנה.

## להתקין על הטלפונים

### דרך א: בכבל USB (הכי נוח לכמה טלפונים)

**פעם אחת בכל טלפון:** מפעילים "אפשרויות מפתחים" ו־"ניפוי באגים ב־USB" (USB debugging). ההוראות המלאות ב־`docs/MOSHE-TODO.md`, שלב E5.

אחר כך:

1. מחברים טלפון אחד, או כמה ביחד (למשל עם מפצל USB).
2. מריצים אחת מהשתיים:
   - `npm run apk -- --install`: בונה ואז מתקין.
   - `npm run apk -- --install-only`: **בלי לבנות**, מתקין את הקובץ האחרון שכבר נבנה. מהיר, בשביל הטלפון הבא בתור.
3. הפקודה מתקינה על כל טלפון מחובר, אחד אחרי השני. לכל טלפון מודפס `installed` (הותקן) או `FAILED` (נכשל) עם ההסבר.
4. מחברים את הטלפון הבא ומריצים שוב `npm run apk -- --install-only`.

במהלך ההתקנה הטלפון צריך להיות פתוח (לא נעול). חלק מהטלפונים שואלים "להתקין?", ומחכים לתשובה.

### דרך ב: להעתיק את הקובץ לטלפון

1. מעבירים את קובץ ה־APK מהתיקייה `apps\mobile\apk` לטלפון: בכבל, ב־Google Drive, או בהודעה לעצמך.
2. פותחים אותו בטלפון.
3. בפעם הראשונה הטלפון שואל אם לאשר התקנה "ממקור לא ידוע". מאשרים.
4. אם Play Protect מזהיר: "פרטים נוספים", ואז "התקן בכל זאת". זו האפליקציה שלך, היא פשוט לא מהחנות.

## למה APK מהמחשב ו־APK מהענן לא מחליפים זה את זה

כל APK **חתום** במפתח, כמו חותמת. אנדרואיד מעדכן אפליקציה רק כשהחותמת של הגרסה החדשה זהה לזו שכבר בטלפון.

- APK **מהמחשב** חתום במפתח בדיקות, שנמצא במחשב.
- APK **מהענן** (EAS) חתום במפתח ש־Expo שומרת אצלה.
- הגרסה **מהחנות** חתומה במפתח של Google.

לכן, בטלפון שכבר יש בו את האפליקציה מהענן: **מסירים אותה פעם אחת**, ואז מתקינים את ה־APK מהמחשב. אותו דבר בכיוון ההפוך.

- ההסרה מוחקת מהטלפון את הנתונים של האפליקציה. החשבון עצמו שמור בשרת, אז פשוט מתחברים שוב.
- אחרי זה, כל APK חדש מהמחשב מתעדכן מעל הקודם, והנתונים נשארים.
- אם שוכחים, ההתקנה נכשלת עם `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. הפקודה מסבירה את זה ומדפיסה את פקודת ההסרה המדויקת.
- `npm run apk -- --install-only --replace` מסיר ומתקין לבד, בכל טלפון שצריך.

## הגרסה לחנות עדיין נבנית בענן

- ה־APK מהמחשב הוא **לבדיקות**: שלך ושל הבודקים. **לא** מעלים אותו ל־Google Play.
- את הגרסה לחנות בונים בענן, עם המפתח של Expo (`docs/MOSHE-TODO.md`, חלק F). זה משתמש בבניות של הענן רק כשמעלים גרסה לחנות.

## כשהדיסק מלא

הבנייה צריכה מקום בכונן C, והמחשב הזה כמעט מלא. לכן:

- **לפני הבנייה** הפקודה עוצרת אם פנויים פחות מ־6 GB, או פחות מ־2 GB כשהבנייה הקודמת עוד שמורה במחשב. בנייה ראשונה כותבת בערך 4 GB, וצריך גם מרווח.
- **באמצע הבנייה** היא עוצרת את Gradle אם נשאר פחות מ־1 GB. כונן C מלא לגמרי שובר את Windows, לא רק את הבנייה.

מה עושים:

1. `npm run apk -- --clean-only` מוחק את קבצי הבנייה הגדולים (בדרך כלל כמה GB). הם נוצרים מחדש לבד, אז הבנייה הבאה תהיה איטית כמו הראשונה.
2. `npm run apk -- --clean` בונה, ובסוף מוחק אותם.
3. מרוקנים את סל המחזור, ומוחקים הורדות ישנות.
4. **סוגרים את Android Studio** ותוכנות כבדות לפני הבנייה. כשהזיכרון מתמלא, Windows מגדיל את קובץ הזיכרון (pagefile) בכונן C, ובזמן הבנייה הוא לוקח עוד כמה GB.

## כשמשהו לא עובד

| מה רואים | מה עושים |
|---|---|
| `cannot build: Java ...` | צריך JDK 17, ו־`JAVA_HOME` שמצביע עליו. |
| `!!! google-services.json is MISSING` | הקובץ של Firebase חסר ב־`apps\mobile\config\firebase`. בלעדיו האפליקציה תיבנה, אבל ההתחברות לא תעבוד מול השרת. מחזירים אותו מהגיבוי (`docs/MOSHE-TODO.md`, שלב B3). |
| `Gradle failed` | כל הפלט נשמר ב־`apps\mobile\apk\last-build.log`. שולחים את הקובץ ל־Claude. אפשר גם לנסות `npm run apk -- --clean-native` (בונה את תיקיית `android` מאפס). |
| `The APK is not right` | הקובץ שיצא לא תקין (למשל, כתובת השרת לא בתוכו). מריצים `npm run apk -- --clean-native`. אם זה חוזר, שולחים את `last-build.log` ל־Claude. |
| `Could not move android/.gradle aside` | תוכנה אחרת מחזיקה את הקבצים, בדרך כלל Android Studio. סוגרים אותה ומריצים שוב. |
| `No phone found` | הכבל מחובר? "ניפוי באגים ב־USB" דולק? יש כבלים שרק מטעינים. |
| `unauthorized` | פותחים את נעילת הטלפון ומאשרים "לאפשר ניפוי באגים ב־USB?". |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | בטלפון יש גרסה מהענן. ראו "למה APK מהמחשב ו־APK מהענן לא מחליפים זה את זה". |
| `INSTALL_FAILED_USER_RESTRICTED` | הטלפון חסם. ב־Xiaomi: להדליק "Install via USB" באפשרויות המפתחים. ב־Samsung: לכבות את Auto Blocker. |

## כל האפשרויות

```powershell
npm run apk -- --help
```

| אפשרות | מה היא עושה |
|---|---|
| `--server <שם>` | השרת: `staging` (ברירת מחדל), `production`, `local`, או כתובת. |
| `--install` | אחרי הבנייה, מתקין על כל הטלפונים המחוברים. |
| `--install-only` | בלי לבנות: מתקין את ה־APK האחרון. |
| `--replace` | עם התקנה: מסיר קודם גרסה עם חותמת אחרת. **מוחק את הנתונים של האפליקציה באותו טלפון.** |
| `--clean` | אחרי הבנייה, מוחק את קבצי הבנייה הגדולים. |
| `--clean-only` | בלי לבנות: רק מוחק את קבצי הבנייה הגדולים. |
| `--clean-native` | בונה את תיקיית `android` מאפס. |
| `--verbose` | מציג את כל הפלט של Gradle, לא רק סיכום. |
| `--dry-run` | רק מדפיס מה ייבנה, בלי לבנות. לא עובד עם `--install-only` או `--clean-only`. |

## לבעלי מקצוע

- הסקריפט: `apps/mobile/scripts/build-apk.mjs`. החלקים בלי קלט/פלט ב־`apps/mobile/scripts/lib/build-apk.mjs`, והבדיקות ב־`apps/mobile/src/__tests__/buildApk.test.ts`.
- השרת נקרא מ־`env` של הפרופיל ב־`apps/mobile/eas.json` (‏`preview` או `production`), כך שהבנייה במחשב והבנייה בענן לא מתפצלות. Metro מכניס את משתני `EXPO_PUBLIC_*` לקוד בזמן הבנייה. קובצי `.env` לא נקראים (`EXPO_NO_DOTENV`), כדי ש־`.env.local` של `dev:lan` לא יחליט לאיזה שרת ה־APK מתחבר.
- החתימה: התבנית של Expo חותמת release במפתח ה־debug שהיא שמה ב־`android/app/debug.keystore`. הסקריפט מוודא את זה ב־`android/app/build.gradle` לפני כל בנייה.
- `expo prebuild` רץ רק כשמשהו ב"שלד" השתנה: התלויות ב־`package.json` והגרסאות שמותקנות בפועל (גם כשרק `package-lock.json` השתנה), ‏`app.json` והקבצים שהוא מפנה אליהם (אייקונים, מסך פתיחה, גופנים), ‏`app.config.ts`, התוספים ב־`apps/mobile/plugins`, קובץ Firebase, הגרסאות של Expo ו־React Native, או `--server local`. טביעת האצבע נשמרת ב־`android/.sf-prebuild-hash`. ב־Expo 57 כל prebuild (גם בלי `--clean`) כותב את תיקיית `android` מחדש, ומוחק את כל מה שנבנה בה. לכן כשאין שינוי הוא לא רץ בכלל, וכשיש, הוא רץ עם `--clean`.
- בבנייה במחשב, `app.config.ts` מוסיף דברים שלא קיימים בענן:
  - `plugins/with-local-native-build.js`:
    - כל ספרייה משתמשת ב־NDK שמותקן כאן, ולא מורידה NDK נוסף (כ־2.5 GB).
    - רק ב־Windows: כל ספרייה מקמפלת C++ בשני קבצים במקביל לכל היותר, ו־Metro אורז את ה־JS עם 2 workers, כדי לחסוך בזיכרון.
    - רק ב־Windows: קוד ה־C++ של האפליקציה נבנה בתיקייה קצרה, `%USERPROFILE%\.sudoku-fight\cxx`. בתוך `android\app\.cxx` הנתיבים עוברים את המגבלה של Windows (260 תווים), והבנייה נכשלת.
  - עם `--server local` (המשתנה `SF_ALLOW_CLEARTEXT`): הרשאה לחיבור בלי הצפנה.
- ה־JS נארז מחדש בכל בנייה (`:app:createBundleReleaseJsAndAssets --rerun`, בערך דקה). בלי זה Gradle מחשיב את החבילה הקודמת כעדכנית, כי הוא בודק רק קובצי `.js` ו־`.ts` בתוך `apps/mobile`: לא את `packages/*`, לא קובצי JSON (הטקסטים), לא תמונות וצלילים, ולא את כתובת השרת.
- Gradle רץ עם 2 workers, מקמפל Kotlin בתוך התהליך שלו (בלי תהליך Java נוסף), ובלי "lint vital" (בדיקת ה־lint של גרסת release). שלושתם חוסכים זיכרון. ה־lint עדיין רץ בבנייה לחנות, בענן. אחרי הבנייה הסקריפט עוצר את ה־daemon של Gradle, כדי לשחרר את הזיכרון.
- prebuild מוחק את תיקיית `android`, ואיתה את ההיסטוריה של Gradle (`android\.gradle`). הסקריפט שומר אותה בצד ומחזיר אותה, כך שהספריות ב־`node_modules` לא נבנות מחדש.
- CMake בונה כל תצורה של ספרייה בתיקייה משלה (`.cxx\RelWithDebInfo\<hash>`), ותצורה חדשה משאירה את הישנה מאחור, 50 עד 400 MB כל אחת. הסקריפט מוחק את הישנות לפני הבנייה ואחריה, ומשאיר רק את החדשה.
