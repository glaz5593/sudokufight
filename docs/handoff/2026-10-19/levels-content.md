  - `kinds.find.name`, ‏`kinds.find.label` ו־`goals.find` בעברית ובאנגלית.
  - `chapters.*.news`: לפי החלוקה החדשה (סעיף 3).

## 4. מלא את הריבוע, השורה והעמודה (סעיף 3) [D67, D68, D69]

### 4.1 מה משתנה
- **מתחילים ב־2 משבצות** בלוח מלא, ועולים לאט עד 9.
- **ככל שעולים, יש פחות ספרות מסביב.** כך יש יותר אפשרויות, וצריך לחשוב.
- **"כל ספרה חסרה לפחות פעם אחת"** מפרק 5 (סעיף 4.2).
- **הטכניקה עולה כמו היום:** בודד גלוי, אחר כך בודד נסתר, צמצום וזוגות.
- **הזמן** נקבע ממודל של זמן למשבצת (סעיף 4.4), עם תקרה של 60 ש׳ (סעיף 4.5).
- **שורה ועמודה:** אותו סולם בדיוק, ואותם ספים.

### 4.2 הכלל "כל ספרה חסרה לפחות פעם אחת"
- **ההגדרה המדויקת:** מחוץ לאזור (הריבוע, השורה או העמודה), לכל ספרה 1–9 יש לפחות משבצת ריקה אחת שזו התשובה שלה.
  - ההגדרה בקוד: `minDigitGaps = 1`, מפרק 5.
- **למה זה עוזר:** כשכל 8 המופעים של ספרה גלויים מסביב, רואים מיד איפה היא באזור. משבצת ריקה לכל ספרה מכריחה לחשוב.
- **איך הבונה מבטיח את זה:**
  1. פתרון מלא, ובחירה של המשבצות החסרות באזור.
  2. **לכל ספרה, בסדר אקראי (seed):** מרוקנים משבצת אחת שלה מחוץ לאזור.
     - אחרי כל ריקון בודקים שהאזור עדיין נפתר לבד, בטכניקות של הפרק.
     - אם לא, מחזירים את הספרה, ומנסים משבצת אחרת של אותה ספרה.
  3. ממשיכים לרוקן משבצות אקראיות, עם אותה בדיקה, עד מספר המלאות של הפרק.
  4. בפרק שדורש טכניקה: בודקים שבלעדיה האזור לא נפתר.
  - **לאזור יש תשובה אחת,** כמו היום: כל צעד של הפותר הלוגי הכרחי.
- **נמדד** (30 ניסיונות לכל שורה בטבלה, בריבוע ובשורה):
  - כל השורות בטבלה נבנות.
  - הכי קשה למצוא: 5 חסרות עם 56 מסביב, שחייבות בודד נסתר. רק 5–6 מתוך 30 ניסיונות מצליחים.
  - הבונה מנסה עד 400 פעם לכל שלב, אז זה מספיק בהרבה.

### 5.2 למה לכל פאזל יש פתרון אחד (נמדד)
- **בלי ריבוע קבוע, תמיד יש לפחות 36 סידורים תקינים.**
  - אפשר להחליף בין "רצועות" שלמות (שורה של שלושה ריבועים), ובין "טורים" שלמים של ריבועים. זה 3! × 3! = 36.
  - ב־60 לוחות אקראיים: 57 עם 36 סידורים בדיוק, ו־3 עם 72.
- **עם שני ריבועים קבועים, ברצועות שונות ובטורים שונים,** ההחלפות האלה נחסמות.
  - ב־60 לוחות: פתרון אחד ב־57 עד 60 מתוך 60, לפי מספר הזזים (3 עד 7).
  - כשיש יותר מפתרון אחד, הבונה פשוט מגריל שוב.
- **הוגן:** כל פאזל עם פתרון אחד במדידה נפתר גם צעד אחר צעד:
  - בכל רגע יש מקום שרק ריבוע אחד מתאים לו. "מתאים" פירושו בלי ספרה כפולה בשורות ובעמודות, מול הריבועים שכבר במקום.
  - או שיש ריבוע שמתאים רק למקום אחד.
  - הבונה בודק את זה לכל פאזל. זו "הטכניקה" של הפאזל, וממנה גם ההסבר "למה?" אחרי השלב.

- **מנוע טהור חדש, `levels/puzzle.ts`,** כמו `find.ts`:

- **ה־host: `LocalPuzzleHost`,** מאחורי אותו `GameHost`.

  - אם זה מסוכן מדי: עותק של כ־230 שורות.
  - `select`, ‏`place`, ‏`tap` ו־`react` מסורבים (`badAction`). אין תגובות בשלב (D62).
- **`GameHost` מקבל פעולה אחת חדשה:** `swapBoxes(from: number, to: number)`.
  - שאר ה־host־ים (`LocalGameHost`, ‏`LocalFindHost`, ‏`RemoteGameHost`) מסרבים לה (`badAction`), כמו ל־`tap` היום.
  - **לחלק הממשק:** במסך זו `session.swap(from, to)`, והיא קוראת ל־`swapBoxes`. המסך תמיד קורא ל־host כשריבוע נעזב על ריבוע אחר, ומגיב לסירוב. הוא לא מחליט בעצמו.
- **`levelOutcome()`** קורא גם את הסוף של הפאזל. המדד: הזמן. ‏`mistakes` = ההחלפות השגויות.
- **`levelOutcome()` מחזיר גם `bossBeaten`**, בשביל "ניצחת את הבוס!" בחלק הממשק:
  - בבוס עם בוט: `true` רק אם ניצחת את הבוט (`verdict = 'won'`). במרוץ אפשר לקבל כוכב ועדיין להפסיד לבוט.
  - בבוס בלי בוט (רק אם תבחר D72 ב): כוכב אחד לפחות.
  - בשלב שאינו בוס: `null`.
- **מה המנוע מייצא** (`packages/engine/src/levels/index.ts`):
  - היום הוא מייצא רק את `spec`, ‏`stars`, ‏`progress`, ‏`transform`, ‏`find` ו־`findHost`. ‏`levels.config.ts` לא מיוצא.
  - נוסף קובץ קטן, `levels/catalog.ts`, עם `kindOfLevel`, ‏`levelRev`, ‏`LEVEL_REV_BASE` ו־`BOSS`. השרת ואתר הניהול צריכים אותם.
  - נתיב א הבעלים של `index.ts`. הוא מוסיף ייצוא ל־`puzzle`, ‏`puzzleHost`, ‏`localLevelHost`, ‏`boss` ו־`catalog`, יחד עם קבצים ריקים ("stub") שהנתיבים ג וד ממלאים. כך אף נתיב אחר לא נוגע ב־`index.ts`.

### 5.5 מה המסך מקבל
```ts
// GameView.level.puzzle
interface LevelPuzzleView {
  /** The 9 places, row-major (0 top-left … 8 bottom-right), LTR. */
  slots: readonly {
    /** A stable id for the animation: the place this box started at, never the place it belongs in. */
    id: number;
    /** 'placed' only when lockOnCorrect is on; without the lock a box in its place still reads 'movable'. */
    state: 'movable' | 'fixed' | 'placed';
  }[];
  moving: number;
  swaps: number;
  /** Swaps that put neither box in its place (each one cost puzzleSwapPenaltyMs). */
  mistakes: number;
  minSwaps: number;
  lockOnCorrect: boolean;
  /** Empty unless LEVEL_RULES.puzzleConflicts allows it for this stage. */
  conflicts: readonly CellIndex[];
}
// GameView.level.progress: { kind: 'swaps'; used: number; mistakes: number }
```
- **הלוח ב־`GameView`:** 81 הספרות של הסידור הנוכחי, כולן כמו ספרות מקוריות.
- **המסך לא מקבל את התשובה:** ה־`id` הוא המקום שבו הריבוע התחיל, לא המקום שלו.

### 5.6 "שוב" [D63]
- **בפאזל:** לוח שקול רק בהחלפת ספרות, בהזזה של רצועות וטורים שלמים, ובהיפוך.
  - **בלי** להזיז שורות בתוך רצועה. כך כל ריבוע זז כיחידה אחת, ובדיוק אותם זוגות של ריבועים מתאימים זה לזה.
  - הריבועים הקבועים והסידור ההתחלתי זזים יחד איתו.
- **במלא את השורה והעמודה:** בלי היפוך (סעיף 4.6).
- **הבודק** בודק גם את הניסיונות 2–8, כמו היום.

### 5.7 מה `levels:validate` בודק בפאזל
- הפתרון תקין, לא מהמאגר המדורג, ולא של שלב אחר.
- `board.grid` שווה לפתרון. הסידור ההתחלתי נשמר ב־`targets.start`.
- מספר הקבועים והזזים לפי הפרק. לפחות שני קבועים, ברצועות שונות ובטורים שונים.
- כל קבוע עומד במקומו. כל זז מתחיל שלא במקומו, והזזים יוצרים מעגל אחד.
- **בדיוק סידור תקין אחד,** בספירה מלאה של כל הסידורים.
- נפתר צעד אחר צעד.
- `lockOnCorrect` לפי הפרק. הוא נשמר בשלב עצמו, כדי ששינוי בהגדרות לא ישנה שלב שכבר נבנה.
- הזמן עד `maxMsOf('puzzle')`, והספים מסודרים.
- "גורר בלי לחשוב" מגיע ל־★★★ בפחות מ־35% מהניסיונות, בכל פאזל מפרק 4 (סעיף 5.3).
- כל אלה גם בניסיונות 2–8.

## 6. בוס: התוכן (סעיף 6) [D72]

- **מה זה בוס, במשפט אחד:** השלב העשירי בכל פרק. קרב אחד מול בוט עם שם ואווטר, קשה יותר מהשלבים שלפניו. אחרי ששיחקת אותו, ויש לך 20 כוכבים בפרק, נפתח הפרק הבא.
- **למה לא ראית בוס:** בפרק 1 הבוס הוא עוד "מלא את הריבוע", עם 5 חסרות במקום 4, ובלי בוט (סעיף 1).
- **ההצעה: כל בוס הוא קרב מול בוט עם שם ואווטר.**
  - **פרק 1:** מרוץ מול Pip, איטי ב־10% (קצב ‎×1.1), כי זה המפגש הראשון. על לוח "מהיר", ביעדים בריבוע.
  - **מפרק 2, כמו היום:** מרוץ בפרקים הזוגיים, ודו־קרב באי־זוגיים. הבוט של הבוס מהיר ב־10% (‎×0.9) מהבוט של השלבים הרגילים באותו פרק (`BOSS.pace`). ‏Overlord בבוס של פרקים 28–30 (שלבים 280, ‏290 ו־300).
  - הלוח של הבוס באותה רמה כמו בשלבים 7–9 (סעיף 5.3.3 באפיון). לכן "לוח קשה" הוא לא הבדל אמיתי, ולא מוצג כזה.
- **עדיין משימה אחת, עד 30 ש׳** (D49). בלי חלקים ובלי מסכי ביניים.
- **מה המנוע נותן למסך:**
  - `boss: true` ו־`bot`, תמיד. בדיקה חדשה: אין בוס בלי בוט (חוץ מ־D72 ב).
  - **פונקציה טהורה חדשה, `bossTraits(level)`.** היא מחזירה רק הבדלים אמיתיים מול השלבים הרגילים של הפרק. **זה החוזה היחיד, וחלק הממשק בונה עליו:**

```ts
type BossTrait =
  | { key: 'firstBot'; bot: string }                // chapter 1: the first bot you meet
  | { key: 'faster'; bot: string; pct: number }     // from chapter 2: pct from BOSS.pace (10)
  | { key: 'overlord' }                             // chapters 28–30
  | { key: 'moreCells'; from: number; to: number }; // only if Moshe picks D72 ב (chapter 1 stays a fillBox)
function bossTraits(level: Level): readonly BossTrait[]; // [] when the stage is not a boss; never more than 2
```

  - הטקסטים דרך `t()`, במסך. ‏`levelOutcome().bossBeaten` אומר אם ניצחת (סעיף 5.4).
- **"איך משחקים":** השלב הראשון מול בוט הוא הבוס של פרק 1. שני "איך משחקים" ברצף זה יותר מדי. לכן לפני L010 מוצג "איך משחקים" של המרוץ, עם תמונה רביעית "זה גם שלב בוס". ‏"איך משחקים" הנפרד של הבוס לא מוצג שם. איך זה נראה: חלק הממשק (D77).
